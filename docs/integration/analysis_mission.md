### 1. 整场流程：每个停车点做什么、用多久

### 3. 工位放置顺序、时间去向、`wheels_first` 和滤波
**顺序**（`_place_item :992-1073`）：
1. `_goto_ring`（`:1560`）：按 survey 的位置一条 F 指令开到这个环。
2. `_obs_ring`（`:1580`）：空爪到观察姿态，或直接伸到上一个环对准时的远近（ring_precorrect）。
3. `servo.run('RING')`：2 帧测量，参数来自 `_zone_servo_kw :1329`（Fs、最多修 6 次、滤波、`wheels_first`）。
4. 记录占环检查 → `read_angles` → 记下 `pose_at`。
5. `TAKE n`（去转盘取物料）。
6. `_return_to_pose`（`:1492`）：AP 回到记下的角度，学转回来的系统偏差，回读一次，差多了再转。
7. `_drop`（`:1355`）：降到 ZPLC、松手、抬到 ZHI，不缩回。

**每次放置的时间去向（模拟）：**

| 阶段 | 默认参数（共 16.0 秒） | 提速参数（共 8.7 秒） |
|---|---|---|
| 开到环 | 1.8 | 1.8 |
| OBS | 0.2 | 0.2 |
| **对准** | **1.4** | **1.3** |
| TAKE | 5.8 | 2.3 |
| 回到对准姿态 | 3.7 | 1.6 |
| 放下 | 2.5 | 1.1 |

**关于"先对准再回去取再放浪费时间"：**
- 每个物料都必须"转盘→环、环→转盘"各大幅摆动一次。先取物料再对准，摆动次数完全一样（都是 2 次），还会让手里的物料挡住圆环白心。
- 真正花时间的是 ID2 的大幅摆动（模拟里 A2R→A2P 是 320°，ASPD 90°/秒约 3.6 秒）和升降，不是对准本身（只占约 1.4 秒）。
- 能真正省时间的办法：
  - 提速参数（420→228 秒）；
  - STM32 里把升降和摆动重叠起来做（`Seq_Take` 现在是严格串行，`arm.c:902`）；
  - 新加一条 STM32 合成指令，把"TAKE + AP(a1,a2) + 下降 + 松手 + 抬起"一次做完，省掉 3～4 次通信往返和树莓派这边 0.2 秒等待加回读（每次约 0.4～0.6 秒）；
  - 如果 ZOBRNG≠ZHI，改成相等，每次省两段升降。

另外，噪声 1.5px、停车误差 15mm（8 种子）时，滤波关失败 32 次，滤波开 1 次。

**为什么 `wheels_first` 帮不上忙：**
- 车轮只管沿圆环那一排，离圆环的远近（ID2）还得靠手臂，所以不能省掉手臂的步数。
- 小步底盘不准时，误差容易变大，被判成"发散"，触发丢 J 重测。
- `wheels_rpm`=60 对 ≤15mm 的小步**没有作用**：STM32 的 `Car_Straight_Closed` 按 SCACC 300 转/分/秒加减速，走 15mm 峰值速度只有约 33 转/分（`chassis.c:934-1000`）。小步有多"慢"由 SCACC 决定。
- 车轮的分辨率并不比手臂好：车轮只能走整毫米，实际误差约 ±1mm；ID1 约 2.6mm/度，最小一步 0.35°≈0.9mm。
- 想要"小而慢的修正"，更有效的是 STM32 的 ATOL 和 ASPDF：ATOL 0.3° 意味着 ID1 到位误差约 ±0.8mm。模拟里 ID1 的到位误差按 0.03° 算，偏乐观。
- 边界 bug：车轮这一步四舍五入成 0mm 时，会直接以"手臂已到行程极限"失败，而不是改用手臂（`visual_servo.py:683-706`）。只有 |jf| 大于约 2.4 倍像素/毫米时才会出现，概率低。

**滤波：**
- 噪声大时明显更稳：失败 9→2、32→1。名义情况下对准稍快，但误差 >1.5mm 的比例略高（11% 对 7%，240 次放置）。
- 可以试：把推算的相对误差从 0.12 调到 0.2（`:567`）；或者最后一次确认用原始测量。

**建议默认值：**
- `zone_filter=True`，`wheels_first=False`。
- 用户一定要先动车轮的话，用 `wheels_min_mm=4`、`wheels_step_mm=15`，并在真车上用 `mtest TEMP 1 force [wheels]` 对比计时后再定。
- 注意 `wheels_first` 也作用于取回和码垛（`_align_covered` 也用 `_zone_servo_kw`）。

### 4. 从开始到结束还缺什么、集成风险（按严重程度排）
1. **QR 可能用到旧码（高）。** STM32 的 `qr_valid` 一直保留（`arm.c:1138-1146`），整个流程里从不发 `QR CLR`（只有 `qr_claw_test.py:106` 用过）。第二轮如果没给 STM32 断电，`_qr` 会马上读到上一轮的码，整轮搬错。修法：在 `_init_arm` 或 go 开始时发 `qr_clear()`。
2. **QR 读不到没有补救（高）。** `ArmError` 直接放弃（`:394-396`）；6 秒后整轮不夹放。可以加：出错后继续重试到超时；没读到时底盘挪 ±20mm 或转几度再读，注意不要静止超过 15 秒；到 RAW 时如果还没有任务码，再问一次 `QR?`。
3. **计时起点不对（高）。** `MissionHooks` 在 `run_mission` 之前就创建了（`map_merge_live.py:429`），`t0`（`:173`）把扫描、规划和等用户输入 `y`（`auto_run.py:269`）的时间都算进去了。应该在开始行驶时重置 `t0`。另外，开始后还要再敲一次 `y`，违反"一键启动、开始后不能碰电脑"，需要一个自动确认或实体按键。
4. **时间到了不会直接回家（高）。** 超时后钩子只是不干活，`drive` 仍然把剩下的停车点全部开一遍（从 ROUGH1 超时算还要约 46 秒）。时间判断也只在每个物料开始前看 `time_left()<0`，而一次放置要 9～16 秒。修法：钩子提供 `time_up()`，`drive` 跳过剩下的停车点、直接重新规划到 START；超时判断要扣掉"预计这一个物料的用时 + 回家时间"。路线先只排第一批。
5. **屏上计数可能不对（中）。**
   - 计数是"指令执行成功"，不是实际确认。
   - 第二批平放的兜底（`:979-986`）规则不给分、还被算进 PLACE。建议直接不放，省 9～16 秒。
   - `raw_any_order` 不按顺序抓的也算进 GRAB。
   - "PLACE 12/12" 里分母是尝试次数；规则要的是"正确放置数"，最好只显示正确数，或分区显示。
6. **急停/出错处理（中）。** 任何 `Abort`（包括底盘转弯误差 >10°、STOW 失败、挪回停车点失败，`:1633/1653`）都会结束整轮：不收臂、不回家、屏上不再更新。可以对不危险的错误改成"不再干活、尽量开回家"。
7. **启动准备可以提前（小）。** 摄像头第一次测量时才打开（`vision.py:378`，含 0.4 秒等待）；机械臂初始化也在 QR 点才做。可以挪到 go 开始或扫描期间。
8. **小问题。** `mission_cli.py:418` 的 `h._any_next` 赋值后没人用；`_zone_servo_kw` 会永久改写 `servo.cfg` 里的 wheels_* 值（无害）。
9. **改进优先级。**
   - 先做：清旧码 → 超时直接回家并重置计时 → 只排第一批加提速参数 → 修第二批兜底和计数。
   - 再做：HANDOFF 第 5 项（发散判断、不把删 J 写进文件）→ 第 3 项 mtest 开关 → 第 2 项测试 → 第 4 项车身斜。
   - STM32 的指令合并和动作重叠收益最大，但要改固件，并且要上车回归测试。
